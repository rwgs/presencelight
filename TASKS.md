- [ ] T7: Recover polling and light state after interruptions.
  - Measured 2026-09-09 during the T6 Graph interruption: while reads fail, one iteration takes about 29 seconds, because the profile batch and the polling read each retry three times through the Polly policy in [GraphWrapper.cs](src/PresenceLight.Core/GraphServices/GraphWrapper.cs) before the 5-second delay. There is no backoff between iterations and no cap on how long an outage is retried at that rate. This is what makes the freshness check coarse, so it is worth repairing here rather than in T6.
  - Also observed in the same run: once the profile batch starts failing it is retried on every iteration for the length of the outage, because `_appState.User` is only populated on success. That is correct behaviour but it doubles the Graph calls during an outage, since the polling read is attempted as well.
  - Upstream [issue 973](https://github.com/isaacrlevin/presencelight/issues/973), `Wrong LED State after reconnection`, belongs to this task rather than to T6. It reports a WLED device on a serial port that loses its connection when the machine docks, after which the light keeps its old state until the user toggles sync off and on. That is the light-side half of recovery, where the write fails and nothing re-establishes the port, whereas the T6 repair was the presence-side half. The reporter asks for periodic state updates, which the Hue path already does by writing the current colour on every iteration; the serial path needs checking against that. Not reproducible here, since this setup has no serial device.
  - Note from the T2/T3 runs, from code reading rather than an observed failure: the loop in [MainWindow.xaml.cs:504](src/DesktopClient/PresenceLight/MainWindow.xaml.cs#L504) breaks and clears `isInteractRunning` whenever `SignedIn` is false, and only `LoadApp` or a sign-in request starts it again. [Index.razor:81](src/PresenceLight.Razor/Components/Pages/Index.razor#L81) sets `SignedIn` back to true on its own when the cached account still authenticates, without restarting the loop, so a sign-out followed by a page initialisation can leave the application signed in with no polling and no sign-in button. The loop also has no timeout or cancellation around its Graph and light calls, and the constructor runs a second unbounded `while (true)` flag-polling loop with a `Thread.Sleep(100)` in it, which is what consumes CPU while idle.
  - Scope: bounded retry/backoff, throttling, cancellation, responsive UI, prevention of overlapping loops and reconciliation after failed writes.
  - Acceptance: reconnect and sleep/resume restore monitoring, including when presence is unchanged; no stuck or duplicate loops.
  - Automated validation: focused transient/throttled responses, failed-write retry and loop-lifecycle checks for repaired code.
  - Manual validation: interrupt/restore internet and bridge access; sleep/resume while using the settings UI.
  - Dependencies: T3, T5 and T6.

Three further upstream matches, none yet offered as pull requests.

- [Issue 983](https://github.com/isaacrlevin/presencelight/issues/983), `Lights don't turn off after Working Hours`, is the same symptom as one of the T6 working-hours repairs but only partly the same cause. The repair here covers an application started or restarted outside working hours, which never applied `HoursPassedStatus` because `previousWorkingHours` began at false in every process, so the light kept whatever colour it had. Anyone who restarts in the evening, or leaves the application running across a weekend, would see the reporter's symptom from that cause alone. The other path, an application running continuously across the end of the working day, was traced and appears correct: the transition fires, `HoursPassedStatus` of `Off` reaches `SetColor` as an `Off` availability, and `HueService` turns the light off. Offer the fix against 983 as one cause rather than as a claim to close it. One neighbouring latent path is worth mentioning in such a report: an `Off` command whose status entry is missing from the settings file throws in `HueService.SetColor` before the `Off` check is reached, which would also leave the light on.
- [Issue 973](https://github.com/isaacrlevin/presencelight/issues/973), `Wrong LED State after reconnection`, is the light-side half of recovery and belongs to T7 rather than T6. See the note against that task.
- The `Off?` checkbox binding in [Statuses.razor](src/PresenceLight.Razor/Components/Shared/Statuses.razor) matches no upstream issue found so far. It affects the Hue, LIFX, Wiz and Yeelight pages alike, so it is worth reporting as well as offering the one-word fix.

- [x] T6: Define and implement freshness/failure indication. Completed 2026-09-09.
  - Agreed 2026-09-09: a stale read drives the existing `PresenceUnknown` status rather than a new hard-coded colour, so the colour is chosen in the same panel as every other status and turning the light off instead stays available through that status's own `Off?` checkbox. The window before presence counts as unknown is 120 seconds by default, adjustable in Settings; 120 was proposed rather than chosen by the user, so change it if it proves wrong in the working-day trial.
  - Implemented 2026-09-09. A failed read used to throw out to the handler at the bottom of the polling loop, which logged one generic line and left the previous colour on the light, so a lost connection quietly kept showing that someone was available. Reads now go through [PresenceFreshness.cs](src/PresenceLight.Core/PresenceServices/PresenceFreshness.cs): a single failure holds the last status, because a poll every few seconds will produce isolated ones, and once nothing has been read for the window the light shows `PresenceUnknown`, the tray tooltip says how long it has been, and [Index.razor](src/PresenceLight.Razor/Components/Pages/Index.razor) labels the displayed status as unconfirmed. A process that starts unable to reach Graph reaches unknown on the same schedule instead of leaving whatever colour the light already had.
  - Verified 2026-09-09 on the installed build, for the working-hours half. With working hours enabled and the application started at 01:48, outside the configured 08:00 to 18:30, it logged `Outside working hours of 08:00:00 to 18:30:00 on Monday|Tuesday|Wednesday|Thursday|Friday; presence is not being followed` once at 01:48:42 and then set the light to `FFFFFF` at 01:48:43, which is `HoursPassedStatus` of `White`. Both are behaviours that did not happen before: the pause was silent, and the end-of-day action was skipped entirely in a process that started outside working hours. Neither line repeated on later iterations. The original settings were restored afterwards and normal presence monitoring resumed at 01:50.
  - Verified 2026-09-09 by interrupting Microsoft Graph. The interruption was scoped to the application alone rather than to the machine: it was started with `HTTPS_PROXY` pointing at a local port with nothing listening, so its outbound HTTPS calls were refused, and with the bridge address in `NO_PROXY` so the light could still be driven. Starting a minimal CONNECT proxy on that port restored access without restarting the application, which is what made the failure and the recovery observable in one process.
  - The first run of that test found the defect the whole task exists to prevent, and it was not where the repair had been made. The profile and presence batch runs earlier in the loop than the freshness check, its failure is not a `ServiceException`, so it escaped the iteration entirely: no polling delay, no working-hours evaluation, and no freshness check. With Graph unreachable from startup the profile is never populated, so the loop never left that branch, and the light sat on `00ff00` for the full three minutes of the outage. A stale green is exactly what [SPEC.md](SPEC.md) forbids. The batch failure is now caught so the iteration continues to the freshness check, which already handles an unreadable presence.
  - Two reporting gaps found by the same test, both now repaired. Entering the holding state was compared against `Fresh`, but the tracker starts at `Unknown`, so an application that started unable to reach Graph stayed silent until the window expired, which is the case most likely to be a real fault. And the recovery message was emitted only from the polling read, while recovery normally arrives through the profile batch, which recorded the success and cleared the state before the message could be produced; both paths now report through one helper called before the success is recorded.
  - Verified end to end on the installed build, all three transitions: `Presence read failed; holding the last status for up to 120s before showing unknown` at 02:25:16, then on the run with the window set to 30 seconds `Presence read failed; holding the last status for up to 30s` at 02:27:44 followed by `Presence has not been read for 59s; showing presence unknown instead of the last status` and the light set to `FFFFFF` at 02:28:43, and on restoring access `Presence readable again after 23s` at 02:25:39 with the light returning to its presence colour. The configured window is therefore honoured rather than hard-coded, and the original settings were restored afterwards.
  - Note for T7, measured rather than read: while reads are failing, one iteration takes about 29 seconds, because the profile batch and the polling read each retry three times through the Polly policy before the 5-second delay. The unknown state is therefore reached at the first iteration past the window rather than at the window itself, which is why a 30-second window reported 59 seconds and a 120-second window reported 147. Bounded retry and backoff belong to T7; the freshness window is wall-clock and correct, it is the check that is coarse.
  - Upgrade path: `PresenceUnknownAfterSeconds` is absent from any settings file written before it existed, which deserialises to zero and would make one failed read enough.   - The `Off?` tick still recorded against `ActivityInACallStatus` turned out to be a defect in the interface rather than a choice anyone made. The user reported that the app does not show that status as off, which was correct. The checkbox was bound with `Checked`, and MudBlazor renamed that parameter to `Value`; because `MudComponentBase` captures unmatched attributes, `Checked` bound nothing and was emitted as a plain HTML attribute, so every checkbox rendered unticked whatever was stored, while `ValueChanged` still wrote the value. The control was write-only: one click set a status to off invisibly, and a fresh page load showed no sign of it. That is how in-a-call came to be off during the colour tests, when the Hue page saved fourteen times. It is now bound with `Value`, so stored statuses display and can be cleared. [HueService.cs:314](src/PresenceLight.Core/Lights/HueServices/HueService.cs#L314) turns the light off for such a status rather than skipping it, and the shipped default in [appsettings.json](src/DesktopClient/PresenceLight/appsettings.json) is `#ff0000` and not disabled, for Hue, LIFX, Wiz and Yeelight alike. The component is shared by all four provider pages, so the defect affected every one of them.
  - Latency, for the application's own share: the interval between reading a presence and the bridge accepting the write was 0.04 s to 0.43 s across the twelve transitions, and the polling loop ran at a 5.24 s median and 5.45 s 95th percentile against its configured 5 s interval. Worst case from the application seeing a change to the light changing is therefore under 6 s. Microsoft Graph's own propagation delay is not isolated by this run, because the time each status was set in Teams was not recorded; observe it in the T8 working-day trial.
  - No missed or coalesced transitions: seven status changes about 10 to 11 seconds apart were each detected individually, against a 5 s poll.

  - Made this checkable: the log previously recorded only the resulting colour, and several statuses share a colour, so a light change could not be traced to the presence behind it. The polling loop now logs each presence change and how long the previous one was held.
